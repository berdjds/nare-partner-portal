# Phase 4: English and Armenian, AI-assisted translation workflow, company/contact configuration

Branch `feat/portal-b2b-cycle-1`. Not merged, pushed, deployed or migrated.

## Decisions applied
* **D4 (AI provider).** The staging site repository uses **DeepSeek** (`lib/ai-translation.ts`, OpenAI-compatible chat endpoint; `DEEPSEEK_API_KEY` is only a commented example in `.env.example` and the key in its settings backup is empty). Whether that account is approved and configured on the live staging server cannot be seen from here, so **no evidence of an approved configuration was found and generation ships disabled**. The portal has a provider-independent interface (`lib/i18n/provider.ts`) with a DeepSeek adapter mirroring the staging one. It turns on only when the portal server environment sets `TRANSLATION_PROVIDER=deepseek` and `DEEPSEEK_API_KEY`. Nothing is coupled to the staging site (no code, storage or runtime call).
* **Data minimisation.** Only a fixed instruction and the English text of one admin-managed field are sent. Only allow-listed content can be translated (service product name/details, template name, template day narratives); request, client, agency, cost and rate data are not translatable by construction. A guard also refuses text containing an email, phone number, booking reference or link (`SENSITIVE_SOURCE`) before anything leaves the server.
* **D5.** English and Armenian live; Arabic is declared (RTL) but disabled: a disabled locale resolves to English.

## What was built
* **UI i18n:** locale table (`lib/i18n/locales.ts`), catalogues (`en` imports the existing content constants so English has one home; `hy`), English fallback then key, `{var}` interpolation, React provider and `useT()`, server locale from cookie, then Accept-Language (enabled locales only), then English. The root layout sets `lang` and `dir`. A language switcher sits in the public header (inside the menu on phones). Translated now: public header and footer, sign-in page (identical localised error for every failure, so account existence still cannot be probed), partner landing, footer contact. **Not translated yet:** landing page body (Phase 5 rewrite), forgot/reset password, partner application, legal documents, all authenticated staff screens, the quotation PDF.
* **Completeness checks:** tests fail if any English key is missing in an enabled locale, if a translation has unknown keys, empty text, mismatched placeholders, or no Armenian script.
* **Armenian typography:** Noto Sans Armenian via `next/font` (same family as the Nare site, self-hosted at build time, unicode-range subset so English pages do not pay for it), applied under `:lang(hy)`. Checked in Chromium at 1366, 820 and 390 px.
* **Managed-content translations:** `Translation` + `TranslationEvent` tables. Versioned rows, only the latest APPROVED is published, drafts (human or AI) never replace it, approval is a separate permission (`content.approve`; drafting needs `content.translate`), approving supersedes and keeps the old row, translations written against changed English are flagged stale and cannot be approved until revised, English is the fallback. AI drafts record provider/model, source hash, actor and time. Admin screen `/admin/translations` shows source and translation side by side with history. Audit rows `translation.draft|ai_draft|approve|reject`.
* **Company/contact configuration:** `ContactProfile` (immutable versions = history). Fields: founded year, general and B2B email, phones, WhatsApp, address, hours, visibility flags, map (Google Maps link, Place ID, coordinates). Global defaults plus a **partial** portal override (unset fields inherit), validation, draft then publish, `/admin/contact`, audit `contact.draft|publish` (ids only). Built-in fallback is the approved data: founded 2019, info@nare.am, reservation@nare.am, +374 91 005046, +374 10 545046, the existing confirmed address. Public site (footer, landing contact block, legal pages, partner application) reads the published profile through the layout. **No map key exists:** the embed is built from coordinates; links and Place ID open Google Maps. A corrupt or unreadable configuration falls back to the defaults.
* **Permissions:** new keys `content.translate`, `content.approve` (ADMIN by preset; PARTNER ceiling excludes them); contact needs `admin.settings`. Admin nav entries follow the same keys.

## Owner decisions and risks
1. **Enable AI translation?** Confirm that sending admin-managed English content (no client data) to DeepSeek is acceptable and that the account used on staging may be reused, then set the two environment variables on the portal server (never in the repository).
2. **Native review of the Armenian UI strings.** They are a first pass for short labels and must be reviewed by a native speaker before being treated as approved.
3. **RTL readiness is structural only:** `dir` follows the locale table, but 70 physical-direction utilities (`pl-`, `ml-`, `left-`, `text-left` ...) in 28 files still need to become logical ones before Arabic can be switched on; that audit belongs with the Phase 5 visual pass. Arabic content and an Arabic font are out of scope here.
4. **Quotation PDFs and partner-facing content are still English.** A resolver (`resolveText`) exists for translated content but is not yet used by the PDF or partner views.
5. **Cache:** the public contact endpoint is cached for 60 s in browsers; the pages read it per request.

## Independent review (read-only) and what changed
No high finding: no way to overwrite an approved translation, to approve without `content.approve`, or to reach the admin APIs without the key. Fixed after the review:
* **M1** Accept-Language now follows the user's order and q-values (`q=0` and malformed entries ignored); an English entry ranked first keeps English.
* **M2** a published global profile replaces the built-in defaults, so an admin can remove the address, hours or founded year; the admin form shows a saved profile exactly as saved.
* **M3** an AI draft is refused (`HUMAN_DRAFT_PENDING`, 409) while a person's draft is waiting for approval.
* **M4** the "may this text leave the server" check now normalises Unicode (NFKC, every digit script), refuses prices, costs, rates, margins and percentages, obfuscated emails, lower-case booking references and short local numbers (7+ digits), and the admin sees the exact text and must confirm before an AI request. Personal names cannot be detected automatically; the confirmation step and the allow-list are the controls.
* **M5** public contact reads are cached in-process for 30 s and dropped on save or publish (the layout still reads the request cookie, so pages stay dynamic).
* **L1** version numbers are computed inside the transaction and a simultaneous save is a clean 409; **L3** approving an AI draft over an approved human translation asks for confirmation; **L4** `goo.gl` and Google redirector links are refused, only `/maps` paths, the `maps.google.com` host and share links pass, userinfo is refused; **L6** the missing-translation check also reports stale approvals.
* Found by the browser re-run, not the review: a history response arriving after the person began typing could blank the translation box (the Save button then looked disabled). Fixed with a typed-since-open guard.

Still open: **L2** the stale-source re-check happens just before, not inside, the approval transaction (a very small window on SQLite); **L5** `next build` now downloads Noto Sans Armenian from Google Fonts, so builds need network access (CI already does; use `next/font/local` with a committed font file if offline builds matter).
